A Model Context Protocol server in production

Professional

Rail Tech Inc. · AI memory platform · 2025–2026

Problem

The platform needed to be reachable from AI coding tools as a first-class integration rather than through a bespoke API each client had to learn. MCP is the emerging standard for that, and it was mid-transition between two transports.

Approach

Implemented both the legacy SSE transport and the newer Streamable HTTP transport on the same route prefix, so older and newer clients could connect without a separate endpoint or a flag day. Three tools exposed: save, inject and feedback.

Technologies & why

Go with the mcp-go library, inside the existing Fiber service so the tools sit next to the retrieval code they call. The MCP server validates its bearer token at connection time rather than through the proxy's ForwardAuth, because a long-lived SSE stream does not fit a per-request auth model.

Result

Working integrations with Claude Desktop, Cursor and Claude Code. The interesting part was not the protocol, it was the connection lifetime problem behind a CDN, which is in the case study.

Edge-to-service authentication with Cloudflare, Traefik and JWT

Professional

Rail Tech Inc. · every protected route on the platform · 2025–2026

Problem

Two very different client types needed authenticating: browser users signing in with Google, and programmatic MCP clients holding an API key. Reimplementing that check inside each service would have meant three places to get it wrong.

Approach

Authenticate once at the proxy. Traefik ForwardAuth bounces every protected route to a small verifier service before the request reaches an application container. Browser users get a first-party JWT after Google ID token verification; API keys are exchanged for short-lived JWTs.

Technologies & why

Traefik because it was already terminating TLS and routing, so ForwardAuth added a control rather than a component. Cloudflare in front for edge and DDoS, with Traefik configured to trust its published IP ranges so the real client address survives the hop.

Result

One place where authentication is decided. Rate limiting keyed to user ID rather than IP, because behind Cloudflare an IP-keyed limit throttles a shared address rather than an abuser. Service middleware still repeats the checks, so a proxy misconfiguration is not a single point of failure.

Jenkins multibranch pipeline with Ansistrano releases

Professional

Armia Systems Ltd. · hosting client applications · 2019

Problem

Deployment depended on who knew the steps for that application. Two engineers deploying the same thing did not necessarily do the same thing, and rolling back meant reconstructing what had been running before.

Approach

A multibranch pipeline so every branch built the same way, with an Ansistrano release layout on the target hosts: timestamped release directories and a symlink swap for the cutover. Plus the branching and release plan around it, so the pipeline matched how the team actually worked.

Technologies & why

Jenkins because it could watch every branch without a job per branch. Ansistrano because it builds on Ansible, which was already how these hosts were configured, and because the symlink-swap layout makes rollback a swap back rather than a redeploy.

Result

Deployment became a pipeline run rather than a remembered procedure, and rollback became switching a symlink to the previous release. I did not measure deployment time before and after, so I am not claiming a percentage.

Ansible baseline for hosting servers

Professional

Armia Systems Ltd. · client server fleet · 2019

Problem

Patching and hardening were per-host and manual. Servers built at different times by different engineers had drifted, so "the same server" was not the same server and a rebuild did not reliably come back the way it went in.

Approach

Wrote playbooks covering the OS baseline, package updates, SSH and sysctl hardening and service configuration, and ran them against the fleet rather than working down a list of hosts by hand.

Technologies & why

Ansible because it is agentless and the hosts already had SSH access. On servers I was trying to reduce work on, an agent would have been one more thing to install, patch and monitor. Idempotent modules over shell commands, so a second run reports nothing changed and the output stays readable.

Result

Patching stopped being a per-host task, and a rebuilt server converged on the same baseline as the rest. That is what made rebuilding a normal action rather than a last resort.

Linux hardening baseline for hosting fleets

Professional

Brookwin Technologies & Armia Systems · shared and VPS hosting · 2016–2020

Problem

Shared and VPS hosting is a permanent target. Compromises arrive through weak file permissions, world-writable temp directories, exposed services and unpatched PHP, and on a hosting fleet one compromised account affects neighbours.

Approach

Built a repeatable hardening pass applied at provisioning and re-checked on rotation: SSH and PAM policy, file permission fixes, noexec mounts for /tmp and /dev/shm, disabling services nobody used, firewall and brute-force protection, and scheduled malware and rootkit scanning.

Technologies & why

CSF for the firewall and login failure daemon, fail2ban for service-level bans, rkhunter and chkrootkit for rootkit checks, maldet with ClamAV signatures for web-shell scanning, OSSEC for file integrity and log-based alerting. Each covers a different layer and misses different things.

Result

New servers went out hardened rather than hardened-later, and the checklist meant it did not depend on which engineer built the box. The notes and configs behind this are the ones now published in my security repository.

Apache and MySQL tuning on shared hosting

Professional

Brookwin Technologies & Armia Systems · hosting client servers · 2016–2020

Problem

Servers that looked healthy on CPU were failing under load: Apache would stop accepting connections, the box would swap, and sites went slow or down while free memory looked fine on a quiet day.

Approach

Measured actual per-process Apache memory, then set MaxClients from available RAM instead of leaving the default. Enabled compression and caching headers to cut the work per request, and on the database side tuned buffers and caches to the workload and used the slow query log to find the queries that were actually hurting.

Technologies & why

Apache prefork with mod_deflate, mod_expires and mod_evasive, because the PHP stack on these servers required prefork. MySQL my.cnf tuning of key buffer, table and thread caches and InnoDB settings, with mysqlcheck on a maintenance rotation.

Result

The failure mode changed from "server swaps and stops responding" to "requests queue and drain", which is a recoverable state. The tuning notes and configs are published in the webservers and mysql repositories.

Incident engineering

Six failures I have actually worked

Tools are learnable. What takes years is knowing where to look. Each of these ends in a prevention step, because a fix that only works once is not finished.

MCP clients silently lose their connection after about 100 seconds of quiet

InvestigationNo error on either side, which ruled out an application-level failure. Reproduced against the service directly and through the CDN. Direct connections held; proxied ones did not.
Root causeCloudflare closes a proxied connection that has been idle for roughly 100 seconds. An SSE stream with nothing to send looks exactly like an idle connection.
FixA 25 second keepalive on the SSE stream, comfortably inside the timeout window rather than at its edge.
PreventionAnything long-lived behind a proxy or CDN gets its keepalive interval checked against that proxy's idle timeout, rather than assumed. It is not in the application's own documentation.

Sites on a shared host stop serving, but df -h shows free space

InvestigationDisk had room, so checked inodes with df -i. One filesystem was at 100% inode use.
Root causePHP session files and a mail queue had accumulated millions of tiny files. Space was free; the filesystem had no inodes left to create anything new.
FixLocated the offending directories by inode count, cleared aged session and queue files, restarted the affected services.
PreventionAdded inode usage to the monitoring alongside disk percentage, and a scheduled cleanup for aged session files.
disk and inode check script → socialp630/linux

Server stops accepting connections under load and starts swapping

InvestigationApache was at its process limit while memory was exhausted. Measured actual resident memory per httpd process rather than assuming the default sizing was right.
Root causeMaxClients was set higher than the RAM could support for that workload, so at peak the server tried to fork more workers than it could hold and went to swap.
FixRecalculated MaxClients from available memory divided by real per-process size, applied it, and enabled compression and cache headers to reduce work per request.
PreventionMade the memory calculation a documented step at provisioning, and alerted on swap activity rather than only on memory percentage.
prefork tuning notes → socialp630/webservers

HTTPS fails for one virtual host while the rest of the server is fine

InvestigationChecked the certificate served on that host and its expiry date against the certificate on disk; they did not match what was expected.
Root causeThe certificate had expired. The renewal had run but the service reload afterwards had not, so the process was still holding the old certificate in memory.
FixRenewed, then reloaded the web server so the new certificate was actually picked up, and verified from outside the host rather than from the filesystem.
PreventionA scheduled expiry check that reads the certificate over the network for every hostname, so it catches "renewed but not reloaded", which a file check misses.
SSL expiry check script → socialp630/linux

Application slow for users, CPU and memory on the host look normal

InvestigationHost metrics were unremarkable, so moved to the database. Enabled the slow query log and watched what accumulated during a slow period.
Root causeA query with no usable index was doing a full table scan on a table that had grown past the point where that was survivable. It was slow, not busy.
FixIdentified the query from the slow log, confirmed the missing index with the execution plan, and raised it with the application side rather than silently altering someone else's schema.
PreventionKept the slow query log on with a sensible threshold and added it to the routine checks, so query regressions surface before users report them.
slow query log notes → socialp630/mysql

Deployment reports success but the service does not come up on one host

InvestigationPipeline was green and the release directory was correct, so the difference was the host. Compared the failing host's configuration and installed packages against a working one.
Root causeConfiguration drift. That host had been fixed by hand during an earlier incident and never brought back in line, so it no longer matched what the deployment assumed.
FixBrought the host back to the baseline through the Ansible run rather than hand-patching it a second time, then redeployed.
PreventionThis is the argument for running the configuration baseline across the whole fleet on a cadence: drift gets corrected on a schedule instead of being discovered during a deployment.

Practice

How I approach infrastructure

Automate the second time, not the first

The first time I do something by hand I am still learning what it actually involves. The second time is when I know enough to write it down properly.

Configuration drift is the real enemy

Most "works on that server but not this one" incidents are a host somebody fixed by hand. Scheduled configuration runs across the whole fleet fix that class of problem, not each instance of it.

Monitor the cause, not just the symptom

Disk percentage without inode usage, memory percentage without swap activity: the alert that fires too late is nearly as bad as no alert.

Know your gaps precisely

An honest inventory of what a system does not have is worth more than an optimistic one of what it does. The same goes for my own skills, which is why the list above is labelled.

Least privilege, and separate environments

Access scoped to the job, secrets out of repositories, and environments kept apart so a test does not reach production data.

Documentation is part of the change

A change that only I can repeat is not finished. Runbooks and version-controlled configuration are what turn individual knowledge into something a team can operate.
