Case study 01 · Infrastructure automation

Replacing per-host patching with a scheduled fleet baseline

Twenty-odd servers across two clouds, patched and hardened one at a time by whoever had the ticket. The job was not to write clever automation; it was to make any host in the fleet converge on the same known state without anyone logging in.

WhereRail Tech Inc.
When2025 – 2026
Scale~20 hosts, AWS and GCP
My roleSole infrastructure engineer on this work
StackAnsible, Linux, Git, cron

Problem

Patching and hardening were per-host and manual. When a CVE needed attention, someone worked down a list of servers by hand. That is survivable at three servers and it is not survivable at twenty, for two reasons that are easy to underestimate.

The first is time. The second, and the one that actually bit us, is drift. Hosts built at different times by different people had picked up different sysctl values, different SSH settings, different installed packages. A host that had been fixed by hand during an earlier incident was never brought back in line. So "the same server" was not the same server, and rebuilding one was risky because nobody could say with confidence what it would come back as.

The symptom that made it urgent A deployment succeeded on every host except one. The pipeline was green and the artifact was correct. The difference was that one host had been hand-patched months earlier and never reconciled. Fixing it by hand again would have reproduced the same problem later.

Environment

  • Roughly 20 Linux hosts split across AWS and GCP, running the services behind a production AI platform.
  • Mixed roles: application hosts, data services, and the supporting infrastructure for CI and monitoring.
  • SSH access already in place to every host, with key-based authentication and a bastion path.
  • A small team. This is the constraint that shapes everything below: there was no separate platform team to hand operational work to.

Constraints

  • No new agents. Anything I installed on every host became one more thing to patch, monitor and debug. That ruled out an agent-based configuration management tool.
  • No downtime window. The platform served live traffic, so the baseline run had to be safe to execute against running hosts.
  • Idempotency was non-negotiable. A scheduled run against the whole fleet is only safe if running it twice is the same as running it once.
  • It had to stay readable. If I was the only person who could understand it, I had replaced one single point of failure with another.

Architecture

Nothing exotic. Inventory in version control, playbooks in version control, a scheduled run from a control host, and results back to where someone will actually see them.

Implementation

I started by writing down what a correct host looked like, because I could not automate a target I had not defined. That list came from the hosting years more than from anything cloud-specific: SSH policy, password and lockout policy through PAM, sysctl values, file permissions, which services should not be running, and the package baseline.

  • Inventory first. Hosts grouped by role rather than by cloud, so a play targets "application hosts" and does not care whether that host is on EC2 or GCE.
  • Roles per concern. Patching, SSH and PAM, sysctl and limits, and service configuration each stand alone, so one can be run, reviewed or reverted without dragging the others along.
  • Idempotent modules over shell. Ansible's package, service, template and lineinfile modules where possible, rather than shelling out. A shell command that is not guarded runs every time and reports changed every time, which destroys the signal in the run output.
  • Check mode before apply. A dry run against the fleet shows what would change. On a stable fleet that output should be nearly empty, so anything in it is worth reading.
  • Everything in Git. A baseline change goes through the same review as application code, and I can say when a value changed and why.

What got automated

  • OS package updates on a schedule, rather than in response to a ticket.
  • The full hardening pass, applied at provisioning and re-asserted on every run.
  • Service configuration, so a config change is a commit rather than an SSH session.
  • Drift correction, which is the quiet one: a host someone touched by hand gets pulled back to baseline on the next scheduled run instead of waiting to surprise a deployment.
The deliberate non-goal I did not try to make the playbooks handle every edge case on every host. A baseline that covers the common case and reports honestly when a host is an exception is more useful than one full of conditionals that nobody can reason about.

Security

  • Key-based SSH only, with password authentication and direct root login disabled as part of the baseline itself.
  • Least privilege for the runner: a dedicated account with scoped escalation, not a shared root key sitting on a control host.
  • No secrets in the repository. Anything sensitive is referenced, not committed, so the playbooks can be read without exposing the fleet.
  • The hardening itself is version controlled, which means a weakening of policy is visible in a diff instead of happening quietly on one host.

Monitoring

Automation that fails silently is worse than no automation, because people stop checking. The scheduled run writes its output where it can be read afterwards, and a failed run raises an alert in the same path as any other production alert. Beyond the run itself, the existing Prometheus and Grafana setup covers the things the baseline is meant to protect: disk and inode usage, memory and swap, and service availability per host.

Result

  • Nobody patches servers one at a time any more. That was the stated goal and it is the honest description of the outcome.
  • A rebuilt host comes back the same as the rest of the fleet, which is what turned rebuilding from a last resort into a normal action.
  • Drift gets corrected on a cadence rather than discovered during a deployment.
  • Baseline changes are reviewable. The fleet's configuration has a history.

I am not going to attach a percentage to this. I did not instrument engineer-hours before and after, and a number I cannot defend in an interview is worth less than the description above.

What I would do differently

I would build the check-mode run into the schedule from day one instead of adding it once I wanted visibility, so drift is reported continuously rather than corrected invisibly. I would also push harder on making the provisioning step call the same roles, so that a new host is baseline-compliant at first boot rather than at the next scheduled run.
