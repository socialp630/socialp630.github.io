Case study 01 · Protocol infrastructure

Running an MCP server on two transports, behind a CDN

I deployed and ran this service; I did not write it. What follows is the part that was mine: a failure that produced no error on either side, clients going quiet and never coming back, and why the CDN in front was responsible.

WhereRail Tech Inc.
When2025 – 2026
ClientsClaude Desktop, Cursor, Claude Code
My roleDeployed, operated, debugged. Not the service author
StackGo, Fiber, mcp-go, SSE, Streamable HTTP

Problem

The platform exposed its memory tools over the Model Context Protocol, which is how an AI coding tool reaches a service without either side knowing about the other in advance. The protocol was mid-transition between transports: an older SSE-based one that deployed clients still used, and a newer Streamable HTTP one that newer clients preferred. Both had to work, from one address, because asking a user to know which transport their client speaks is not a reasonable thing to ask.

That much was working when I took it over. The problem I own is what happened next. Clients would connect, work normally, and then stop receiving anything. No error. No disconnect event the client surfaced. The stream was simply dead, and only restarting the client brought it back. Roughly a hundred seconds of quiet was the pattern, but it took a while to see the pattern at all, because an active user never hit it.

Environment

  • A Go service built on Fiber, already holding the tag graph and retrieval logic the MCP tools would need to call.
  • Traefik in front for routing and TLS, with ForwardAuth handling authentication for the rest of the platform.
  • Cloudflare in front of that as the edge layer.
  • One Compute Engine VM running everything under Docker Compose.

Constraints

  • I could not read my way to the answer. I did not write the service, so "read the code until the bug appears" was not the fast path. The path was to treat it as a black box and narrow down where the failure lived.
  • It was intermittent and invisible. Nothing logged it, nothing alerted on it, and it only happened when a user went quiet, which is exactly when nobody is watching.
  • No flag day. Whatever the fix was, connected clients could not be asked to reconfigure.
  • Long-lived streams do not fit per-request auth. The platform's ForwardAuth model could not be applied to this route, so it had to be handled as a documented exception rather than an oversight.

What I ran, and what I owned

Worth being precise about, because it is the difference between this case study and one a developer would write.

  • Not mine: the Go service, the mcp-go integration, the three tools it exposes, and the choice to support both transports.
  • Mine: deploying it, keeping it serving both transports behind one route prefix through Traefik and Cloudflare, the authentication exception for the route, the diagnosis below, the fix, and the rule I now apply to anything long-lived behind a proxy.

The authentication exception is worth a line. Every other protected route on the platform goes through the proxy's ForwardAuth, which verifies per request. A stream that opens once and lives for hours cannot work that way, so this route validates its bearer token at connection time instead. That is a deliberate, documented difference rather than a gap somebody left, and knowing which of the two it is was part of running it safely.

The failure worth writing down

Clients would connect, work normally, and then stop receiving anything. No error. No disconnect event the client surfaced. The stream was simply dead, and only a restart of the client brought it back. Roughly a hundred seconds of quiet was the pattern, but it took a while to see the pattern at all, because an active user never hit it.

Investigation

  • No error meant it was not the application. An application-level failure leaves something behind: a log line, a panic, a closed-with-reason. There was nothing, which pointed at something in the path closing the socket without telling either end.
  • Split the path. Connected directly to the service, bypassing Cloudflare, and left it idle. The stream held. Connected through Cloudflare and left it idle, and it died. That isolated it to the edge in one test.
  • Matched the timing to the documented behaviour. Cloudflare closes a proxied connection that has carried no traffic for around a hundred seconds. An SSE stream with nothing to send is, from the outside, indistinguishable from a connection nobody is using.
Why this is easy to miss It is not a bug in the protocol, the library, or the application, and none of their documentation mentions it. It only exists at the intersection of a long-lived stream and an intermediary with an idle policy, and it only shows up when a user goes quiet, which is exactly when nobody is watching.

Fix

A 25 second keepalive written to the SSE stream. The interval is deliberately well inside the timeout rather than close to it: at roughly a quarter of the window, three consecutive ticks can be delayed or lost and the connection still survives. Setting it at 90 seconds would technically satisfy the timeout and would fail the first time anything hiccuped.

Security

Not my design, but my responsibility to understand and keep intact while operating it. The route validates its bearer token when the connection opens, since per-request ForwardAuth does not apply to a persistent stream. API keys are exchanged for short-lived JWTs rather than the long-lived key travelling with every call. Rate limiting is keyed to user ID, which matters here because MCP traffic arrives from a small number of client applications.

Monitoring

Prometheus and Grafana covered the service's metrics. The honest limitation is that this specific failure would not have been caught by them as configured: an idle connection dying looks like a user who stopped working. Catching it would need a synthetic client that connects, goes deliberately quiet past the timeout, and reports whether the stream survived. That is on my list for the platform rather than something I can claim I had running.

Result

  • Working integrations with Claude Desktop, Cursor and Claude Code, on whichever transport each one speaks, from one address.
  • Connections survive idle periods, which is the difference between a tool people keep configured and one they quietly remove.
  • A rule I now apply generally: anything long-lived behind a proxy gets its keepalive interval checked against that proxy's idle timeout before it ships.

What I would do differently

I would have built the synthetic idle-connection probe first. The fix took an afternoon once the cause was clear; finding the cause took much longer, because the failure was invisible to everything we were measuring. A monitor that deliberately does the thing users do accidentally would have turned a mystery into an alert.
