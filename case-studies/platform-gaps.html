Case study 04 · Analysis, not implementation

Auditing a platform I ran, and naming what it did not have

A working production system, built and operated by two people under a funding pause. It served real users for over a year. It also had no CI/CD, no infrastructure as code, and alerting that never reached anyone. This is the inventory, why each gap existed, and what I would fix first.

WhereRail Tech Inc.
When2024 – 2026
TeamTwo people
StatusAnalysis and design, not built
ScopeOne Compute Engine VM, four services

Why this page exists

Most portfolios describe what a system had. This one describes what mine did not have, because that turned out to be the more useful thing to be able to discuss.

The platform worked. Real users, real traffic, uptime that was fine, a genuinely uncommon piece of protocol engineering inside it. It was also, by any honest definition, operations rather than DevOps: built by hand, deployed by hand, and monitored by someone looking at a dashboard. Both of those statements are true at once, and being able to hold them together is the point.

Explicitly not implemented Everything in the "would do" column below is a design, not something I built. I left the company before this work started. It is here because the analysis is mine and I can defend every line of it, not because I am claiming the outcome.

Why the gaps existed

Not because nobody knew better. Two people, a funding pause, and a product that had to exist before anything else mattered. Every hour spent on a deployment pipeline was an hour not spent on the thing users were there for, and at that size the manual path is genuinely cheaper right up until the moment it is not.

That reasoning is defensible for the first few months. It stops being defensible once the system has real users, and the honest assessment is that we passed that point without revisiting the decision. The cost was not an outage. It was that nobody could safely deploy except the person who always deployed, and that a failure at 3am would have gone unnoticed until somebody happened to look.

The one that bothers me most Not the missing CI/CD. The alerting. Installing Prometheus, Grafana and Alertmanager and then leaving the receiver as a placeholder is worse than having no monitoring at all, because it looks like coverage. Anyone glancing at the stack would reasonably assume failures were being surfaced. They were not.

What I would do, in order

1. Close the alerting loop

A real receiver, then alert rules that matter: host and container down, restart loops, disk and inode usage, memory and swap, certificate expiry, 5xx rate at the proxy, datastore availability. Then induce each failure deliberately and confirm the alert arrives, because an untested alert rule is a guess.

First because it is the cheapest by far, it is entirely additive, and until it is done every other improvement is being made to a system that cannot tell you when it is broken.

2. Backups, with a tested restore

Scheduled dumps of the primary datastore to object storage with lifecycle rules, and then, non-negotiably, a restore into a scratch instance to prove the backup is real. A backup nobody has restored from is a hypothesis.

Second because it is the only gap on the list where the worst case is unrecoverable rather than merely painful.

3. Secrets out of the .env

Either a managed secrets service or encrypted secrets committed alongside the code with keys held outside it. The specific tool matters less than the property: secrets stop being a file that exists in exactly one place, on the host, with no history and no rotation path.

4. Infrastructure as code

Terraform describing the VM, its networking and firewall rules, with state in object storage. The immediate value is not automation, it is that the infrastructure stops existing only as itself. Right now, if that VM is lost, rebuilding it means remembering.

This also makes the next step affordable, because a staging environment you can create and destroy on demand costs almost nothing compared to one that runs permanently.

5. A pipeline, and a staging environment to point it at

Build and test on push, produce a tagged image, deploy to staging automatically and to production on approval. Tagged images rather than rebuilding on the host, so what was tested is what runs and a rollback is applying a previous tag.

Fifth rather than first, deliberately. A pipeline that deploys straight to production with no environment to catch anything is faster manual deployment, not safer deployment.

6. Log aggregation

Shipping container and proxy logs somewhere queryable, so an error rate spike on a dashboard can be clicked through to the lines behind it. Lower down the list than it might look, because with four services on one host, docker logs is slow but it does work. It becomes urgent the moment there is more than one host.

What I would not do

Kubernetes. Four services on one VM with two engineers is not a Kubernetes problem. Adopting it would add a control plane, a networking model and an upgrade cadence to a team that did not have capacity to wire up an alert receiver. The honest sequence is to fix deployment and observability first, and revisit orchestration when the number of services or the availability requirement actually demands it.

Multi-region, or high availability, yet. A single VM is a real risk, but it is a smaller risk than having no tested backup. Removing the single point of failure before you can restore from one is solving the second problem first.

Rewriting anything that works. Traefik, the auth path and the MCP server were fine. The gaps were around the system, not inside it.

What I took from it

  • An installed tool is not an implemented practice. Alertmanager was running for over a year and did nothing. The check is not whether it is up, it is whether it has ever produced the outcome it exists for.
  • Constraints justify a decision, not its permanence. Deploying by hand was right at the start and wrong later, and nothing forced a re-examination because it kept working.
  • Backups are the only gap where the worst case is final. Everything else on that list costs time. That one can cost the product.
  • Knowing what a system lacks is a skill. Being able to produce this list about my own work, without being prompted by an incident, is the thing I would most want to demonstrate to anyone hiring me.
