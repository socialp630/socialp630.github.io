Case study 02 · CI/CD

Making deployment a pipeline run instead of a remembered procedure

Every service on the platform shipped through a build that produced a tagged image and a deployment that applied it. The interesting part was not the tooling; it was deciding what not to rewrite.

WhereRail Tech Inc.
When2025 – 2026
ScopeEvery service on the platform
My roleBuilt and maintained the pipelines
StackJenkins, GitHub Actions, Docker, kubectl, Git

Problem

Releases depended on who knew the steps for that service. Some had a Jenkins job, some had a script, some had an engineer with a terminal and a good memory. Two people deploying the same service did not necessarily do the same thing.

The practical costs showed up in two places. Rolling back meant reconstructing what had been running before, because there was no single record tying a running version to a commit. And onboarding anyone onto a service meant transferring the deployment procedure out of someone's head, which is slow and lossy.

Environment

  • A production AI platform on AWS and GCP, roughly 20 hosts, with workloads moving onto EKS and Docker as traffic outgrew single hosts.
  • An existing Jenkins installation already carrying multibranch builds for the older services.
  • Newer repositories on GitHub, where the team was already reviewing code.
  • A small team with no dedicated build engineer, so whatever I built I also had to keep running.

Constraints

  • Do not rewrite what works. Migrating functioning Jenkins multibranch builds to another tool would have spent weeks to arrive at the same behaviour.
  • One artifact type. Whatever the build system, the output had to be the same kind of thing, or deployment would fragment again.
  • Deployable by someone who is not me. The point of the exercise was removing the dependency on individual knowledge.
  • Secrets stay out of repositories. Non-negotiable, and easy to get wrong when you are moving fast.
The call I made Two CI systems is not ideal and I would not design it that way from scratch. But the cost of standardising was real and the benefit was cosmetic: both paths already produced the same artifact and deployed the same way. I standardised the artifact and the deployment step, and left the build systems where they were.

Architecture

Implementation

  • One trigger model. A push to the tracked branch starts the build. No manual job runs as the normal path, because a manual path is where procedures start diverging again.
  • Build and test in the same run. A failing test stops the pipeline before an image exists, so a broken build cannot be deployed by mistake.
  • Tagged images, not "latest". Each build produces an image identified by its commit, which is what makes "what is running in production right now" an answerable question and a rollback a matter of applying a previous tag.
  • Deployment applies manifests. Kubernetes manifests applied with kubectl, kept alongside the service rather than in someone's shell history.
  • Jenkinsfile in the repository for the Jenkins-side services, so the pipeline definition is versioned with the code it builds instead of living in the Jenkins UI.
# the shape of it, per service
push to branch
  → build + unit tests        # fails here, nothing ships
  → docker build, tag by commit
  → push to registry
  → kubectl apply manifests
  → watch rollout, alert on failure

Security

  • Secrets injected at run time from the CI system's own credential store, never committed and never baked into an image.
  • Scoped deploy credentials. The pipeline's access is limited to what deploying requires, rather than reusing an administrative identity because it was convenient.
  • Registry access controlled, so images are pulled by the cluster rather than being publicly readable.
  • Review before merge as the gate. The pipeline enforces that what deploys is what was reviewed, which only holds if the branch is protected.

Monitoring

A deployment is not finished when the pipeline goes green. Rollout status is watched after apply, and the service's own metrics in Prometheus and dashboards in Grafana are what tell us whether the new version is actually healthy rather than merely started. A failed build or failed rollout raises an alert on the same path as any production alert, because a build system nobody notices failing quietly stops being a control.

Result

  • Deployment became a pipeline run rather than a set of remembered steps, which was the whole point.
  • Every release has a build record attached to a commit, so what is running and what changed are both answerable.
  • Rollback is applying a previous tag instead of reconstructing a previous state.
  • A broken build cannot reach production, because the artifact is never produced.

I did not measure deployment time before and after, so I am not going to claim a percentage improvement. The change that mattered was in who could deploy and how repeatable it was, not in the clock.

What I would do differently

I would put the deployment step behind a proper environment promotion rather than letting the same pipeline shape serve every target, and I would add an automated rollback trigger on failed health checks instead of relying on someone watching the rollout. I would also consolidate onto one CI system eventually, but as a planned migration with a reason, not as a tidiness exercise in the middle of shipping.
