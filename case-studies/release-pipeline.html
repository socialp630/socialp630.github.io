Case study 03 · CI/CD

Making deployment a pipeline run instead of a remembered procedure

Deployment depended on who knew the steps. A multibranch pipeline and a release layout where rollback is a symlink swap turned it into something any engineer on the team could run, and undo.

WhereArmia Systems Ltd.
When2019
ScopeHosting client applications
My roleBuilt and ran it
StackJenkins, Ansistrano, Ansible, Git

Problem

Deploying an application meant knowing that application's steps. Some of it was written down, some of it was in somebody's shell history, and the parts that mattered most were the parts nobody had thought to record because they were obvious to whoever did them last.

Two costs followed. Rollback meant reconstructing what had been running before, under exactly the time pressure that makes reconstruction go wrong. And any engineer who had not deployed that application before could not do it safely, which meant deployments clustered around whoever had, whether or not they were available.

The failure that made it urgent A deployment that needed backing out, where getting to the previous state meant redeploying an older commit and hoping the environment came back the same way. It did, eventually. The problem was that nobody could say in advance whether it would.

Environment

  • Applications running on hosting client servers, Linux, deployed to filesystem paths served by a web server rather than to containers.
  • Ansible already in use for server configuration and the patching and hardening rounds, so the hosts were already reachable and already had a configuration baseline.
  • Git for source, with branches per feature and a release process that was more convention than process.
  • A small team carrying support alongside project work, which is the real constraint: anything that needed constant attention would not survive a busy week.

Constraints

  • No containers. These were conventional application deployments onto servers, so the artifact was a directory of files, not an image.
  • Rollback had to be fast and certain, not "redeploy the previous commit and see".
  • A job per branch was not sustainable. Creating and deleting Jenkins jobs by hand as branches came and went is work that gets skipped, and then branches build differently from each other.
  • The process had to match how the team actually worked, not how a tutorial assumes a team works. A pipeline that does not fit the branching model gets bypassed.

Architecture

Implementation

  • Multibranch, so every branch builds the same way. Jenkins discovers branches itself and applies one pipeline definition to all of them. Nobody creates a job when a branch appears, so nobody forgets to, and a feature branch is tested by the same steps that will eventually deploy it.
  • The pipeline definition lives in the repository. A Jenkinsfile beside the code, versioned with it, rather than configuration clicked into the Jenkins UI where it has no history and no review.
  • Ansistrano for the deploy, over the inventory we already had. It builds on Ansible, which was already how these hosts were configured, so deployment used the same connection method, the same inventory and the same credentials as everything else. No second access path to secure.
  • A release directory per deploy. Each deployment unpacks into its own timestamped directory. Nothing overwrites the running code, which means the previous release is still sitting there, intact, at the moment the new one goes live.
  • Shared state stays out of releases. Configuration, uploads and logs live in a shared directory linked into each release, so they survive a deploy and a rollback rather than being replaced by whatever the new release shipped with.
  • The cutover is a symlink. The web server serves a path that is a symlink to the current release. Deploying points it at the new directory. That is the entire switch: near-atomic, and the state before it is still on disk.
  • A branching and release plan around it. Which branches deploy where, what gets cut for a release, how a hotfix reaches production without dragging unfinished work with it. The pipeline only helps if the team's workflow and the pipeline agree about what a release is.
# what a host looked like after a few deploys
/var/www/app/
  releases/
    2019-06-11-0917/
    2019-06-13-1530/
    2019-06-14-1042/   # newest
  shared/              # config, uploads, logs - survive deploys
  current -> releases/2019-06-14-1042/

# rollback
current -> releases/2019-06-13-1530/     # one symlink, seconds

Why rollback was the point

Most of the value here is not in deploying faster. It is in the fact that going back is a symlink swap against a directory that is already on disk, already unpacked, already the exact bytes that were working ten minutes ago.

The alternative, redeploying a previous commit, is a build. It pulls dependencies that may have moved, runs steps that may behave differently, and produces something you believe is the old version rather than something you know is. Under incident pressure, the difference between those two is the difference between a two minute recovery and an unbounded one.

Security

  • Deploys used the existing Ansible access path, key-based SSH to hosts that already had a configuration baseline. No second credential set to manage or rotate.
  • Configuration out of the repository. Application config lives in the shared directory on the host, not in the release, so credentials are not in source control and not in a build artifact.
  • Credentials held by Jenkins and injected at run time rather than written into the pipeline definition, which is in the repository and therefore readable by anyone who can read the code.

Monitoring

Build and deploy results were visible in Jenkins per branch, so a failing branch was obvious without anyone going looking. On the host side, the existing monitoring covered whether the application was actually serving after a deploy, which is the check that matters: a deploy can succeed and the service can still be down, and only the second one is what users experience.

Result

  • Deployment stopped depending on who remembered the steps. That was the goal and it is the honest description of the outcome.
  • Rollback became a symlink swap to a release still sitting on disk, rather than a rebuild under pressure.
  • Every branch built the same way, so a branch was tested by the process that would eventually ship it.
  • The pipeline had a history, because its definition lived in the repository with the code.

I did not instrument deployment time before and after, so there is no percentage here. What changed was who could deploy and how confidently they could undo it.

What I would do differently

I would add an automated health check after the symlink swap, with an automatic revert if it fails, rather than relying on someone watching. The mechanism for rollback was already there and fast; not wiring it to a check was leaving the best part of the design manual.

I would also keep fewer releases on disk with an explicit retention rule. Release directories accumulate quietly and, on a hosting server where disk is shared, that is a slow leak that eventually becomes somebody's incident.
