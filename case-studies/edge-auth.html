Case study 02 · Edge and authentication

Deciding authentication once, at the proxy

The proxy, edge and TLS layer were mine to configure and operate. The services behind them were not. This is the auth path as I ran it: what I set up, what I only had to understand, and the one call in it that started as a problem I spotted.

WhereRail Tech Inc.
When2025 – 2026
ScopeEvery protected route on the platform
My roleConfigured and operated the edge and proxy layer
StackTraefik v2.11, Cloudflare, Node/Express, Google OAuth, JWT

Problem

The platform had three services written in three languages, and two entirely different kinds of caller. A browser user signs in with Google and expects a session. A programmatic client holds a long-lived API key and expects to present it on every call.

The obvious approach is for each service to check credentials itself. With three services that means three implementations of the same security-critical logic, three places for a bug to live, and three things to update when the rules change. That is not a theoretical risk; it is how authentication drifts apart between services.

Environment

  • Three backend services: a Go tagging service, a Python tag extraction service, and a Node auth service.
  • Traefik v2.11 already terminating TLS with Let's Encrypt and routing to those containers.
  • Cloudflare in front for edge caching and DDoS protection.
  • A React frontend on Vercel, served separately from the API.
  • All backend containers on one Docker Compose bridge network on a single VM.

Constraints

  • One decision point. Authentication had to be decided in exactly one place, or it would drift between services.
  • But not a single point of failure. If the one decision point is misconfigured, everything behind it is open. That tension is the interesting part of this design.
  • Long-lived streams do not fit per-request auth. The MCP endpoint had to be handled differently and deliberately, not accidentally.
  • The real client IP had to survive the edge. Everything downstream that cares about who is calling depends on it.

Architecture

What I configured, and what I inherited

Worth separating, because the line between the two is exactly the line between infrastructure and application here.

  • Mine: Traefik routing and Let's Encrypt TLS, wiring ForwardAuth onto every protected route, and configuring Traefik to trust only Cloudflare's published IP ranges for forwarded headers. Without that last one, anyone reaching the origin directly could assert whatever client IP they liked, and every decision downstream that uses the client address would be built on a value the caller chose.
  • Not mine: the verifier service itself, the token issuing and exchange logic, and the middleware chain inside each service.

The shape of the thing: Traefik sends every protected request to the verifier's endpoint before routing it. A 200 lets it continue to the application container; anything else stops it at the proxy. Browser users sign in with Google and receive a first-party JWT; programmatic clients exchange an API key for a short-lived one. Downstream they look the same, so nothing behind the proxy needs to know which path a caller came through.

The MCP route is a documented exception. A stream that opens once and lives for hours cannot be re-verified per request, so it validates its bearer token at connection time. Knowing that this is a deliberate difference and not a gap somebody left was part of operating it.

The duplication below the proxy

The services repeat work Traefik has already done. Their middleware runs logging, CORS, security headers, input validation, threat detection, rate limiting, and then JWT verification again, on requests that have already passed ForwardAuth.

That is application-side and not my code, but understanding why it is there mattered for running the proxy safely. A single decision point is this design's strength and its weakness at once: one misconfigured router, one route added without the middleware attached, and everything behind it is exposed. The duplication means a proxy mistake produces a rejected request rather than an open door. Knowing that changed how carefully I treated every routing change I made.

The ordering matters Cheap rejections come first. There is no point spending a JWT verification on a request that fails input validation, and no point rate-limiting a request that CORS will reject. The chain is arranged so the most expensive check is the last one a request reaches.

The rate limit that was catching the wrong people

The default for rate limiting is to key on IP. Behind Cloudflare that is actively wrong, and when the problem surfaced I was the one who said so.

The edge collapses many real users behind a small set of addresses, so an IP-keyed limit does not throttle an abuser, it throttles a shared Cloudflare exit address and everyone who happens to be behind it. The fix is to key on something that identifies an account rather than a network path, and by the time a request has passed ForwardAuth there is an authenticated identity available to key on. I raised it; it was implemented as a user-ID key.

This is the kind of thing that only shows up once real traffic arrives through a CDN, and it is invisible if you are reasoning about the application in isolation rather than about the whole path a request takes.

Known gaps

Two I would name before anyone asked. The Cloudflare IP allowlist is hardcoded with no automated refresh, so when Cloudflare publishes new ranges the configuration is silently stale until someone updates it by hand. That should be a scheduled job that fetches the published list and reloads, and it is not.

Secrets lived in a .env file on the VM rather than in a secrets manager. That is the single change I would make first if I were still running this.

Result

  • One place where authentication is decided, enforced at the proxy I configured and maintained.
  • The real client address survives the edge, so everything downstream that depends on it is built on a value the caller cannot choose.
  • Rate limits land on the right account rather than on a shared edge address, after I identified why the original key could not work.
  • A proxy misconfiguration is not a breach, because the services still check.

What I would do differently

The allowlist refresh should have been automated from the start; it is a small job that turns into a confusing outage the day it matters. I would also have put a test in front of the routing configuration that asserts every protected route actually has the middleware attached, because the failure mode of this design is a route quietly added without it, and that is exactly the kind of thing a test catches and a person does not.
