Putting a first-pass diagnosis in front of the pager

A small team carrying an always-on pager spends most of its night on a short list of repeat causes. I put a diagnosis step between the alert and the human, and let a deliberately narrow set of known-safe actions clear themselves.

WhereRail Tech Inc.
When2025 – 2026
ScopeProduction alerting path
My roleDesigned and built it; also the person being paged
StackPrometheus, Alertmanager, Python, OpenAI and Anthropic APIs

Problem

On a platform of around twenty servers with a small team, the pager is not usually ringing about novel failures. It is ringing about the same handful of things: a service that has stopped and needs restarting, a disk filling up with logs, a job that failed and will pass on retry, a host briefly unreachable.

Two costs come out of that. The obvious one is time spent at 2am on something that did not require judgement. The less obvious and more damaging one is alert fatigue: when most pages turn out to be routine, the response to all pages gets slower, including the page that actually mattered.

Environment

  • Prometheus and Alertmanager already in place as the alerting path, with Grafana dashboards and defined SLO targets on the services that had them.
  • Roughly 20 hosts across AWS and GCP running a production AI platform, some on EKS and some still single-host.
  • An always-on pager carried by very few people, which is the constraint that makes this worth building at all.
  • A platform already built around LLM APIs, so calling one from operational tooling was not a new dependency for the organisation.

Constraints

  • A wrong automated action is worse than a page. This governed every decision below. An unnecessary wake-up costs an hour of sleep; an automated action on a wrong diagnosis can cost data.
  • The human stays in the loop for anything not on the list. The tool drafts; it does not decide.
  • It must not become a new single point of failure. If the diagnosis step is down or slow, the alert still has to reach a person.
  • No sensitive data leaving the environment carelessly. What gets sent to an external API needed thinking about, not just piping logs at it.
The design principle Automate the action, not the judgement. The allow-list contains things that are safe even if the diagnosis was wrong: restarting a stateless service, clearing aged log files. Nothing that deletes data, changes configuration, or touches a database is on it.

Architecture

Implementation

  • Sits in front of notification, not in place of detection. Prometheus rules and Alertmanager routing were already correct and I did not touch them. The triage step is a receiver, so if I removed it tomorrow the alerting path still works.
  • Context gathering is deterministic code, not the model's job. A Python step pulls the recent logs for the affected unit, the relevant metric series, and the host and service state. The model gets a consistent, bounded picture rather than whatever it thought to ask for.
  • The prompt asks for a shape, not an essay. A likely cause, the evidence it came from, and a suggested action from a known vocabulary. A free-text answer is not machine-checkable against an allow-list.
  • The allow-list is code, not model output. The model suggests; a hard-coded match decides. If the suggested action is not an exact member of the list, it pages. There is no fuzzy matching, deliberately.
  • Every automated action is recorded with the alert, the diagnosis and the result, so an automatic fix is still reviewable the next morning.
  • Repeat suppression. If the same alert on the same host auto-remediates more than a set number of times in a window, it stops auto-remediating and pages instead, because a recurring symptom is a real problem being hidden.
# the decision, roughly
alert fires
  → gather logs + metrics        # deterministic
  → ask model for cause + action # drafting only
  → action in ALLOWLIST?
       yes and under repeat limit → run it, log it, resolve
       otherwise                  → page, with the draft attached

Security

  • Bounded context. What gets sent is the alert, the relevant metric values and a scoped slice of logs for the affected unit, not arbitrary filesystem or database content.
  • API credentials held by the service, injected at run time, not present in the repository or on the hosts being diagnosed.
  • Least privilege for the action runner. It can restart the specific services it is allowed to restart and clean the specific paths it is allowed to clean. It does not hold general administrative access, so a compromise of the triage service is not a compromise of the fleet.
  • The allow-list is the security boundary, which is why it lives in reviewed code rather than configuration that could be edited casually.

Monitoring

The triage service is monitored like any other production service, because a silent failure in it would mean alerts going nowhere. Its own health and error rate are on the dashboard alongside everything else, and the bypass path means an outage in it degrades to ordinary paging rather than to silence. Auto-remediations are counted, so a rising rate is visible as a signal that something underneath is getting worse.

Result

  • Routine restarts and disk cleanups clear themselves, with a record of what was done and why.
  • The pages that do reach a human arrive with a first hypothesis and the log lines behind it, so triage starts from something rather than from an empty terminal at 2am.
  • Repeat auto-remediation surfaces instead of hiding. A symptom that keeps coming back becomes a page and then a root cause investigation, which is the outcome I actually wanted.
  • The alerting path did not become more fragile, because the triage step can fail without taking paging with it.

I have not put a number on pages avoided. I know which classes of alert now clear themselves and I can describe them; I did not run a controlled before-and-after, so I am not going to present one.

What I would do differently, and where I am cautious

I would put more effort into measuring diagnosis quality. Right now a wrong draft is harmless because the allow-list is narrow, but if I wanted to widen that list I would need evidence about how often the first-pass diagnosis is actually right, and I would want that before widening anything rather than after.

I am also aware of the failure mode where a team stops thinking because a machine offered an answer first. The draft is framed as a hypothesis with its evidence attached for that reason: the point is to save the first ten minutes of gathering, not to replace the judgement that comes after.
